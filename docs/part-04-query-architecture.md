# Part 4: Query Architecture


## 4.1 Overview

The following sections explain how these stages are generated from the SQL query and executed on BE nodes.

An Apache Doris query consists of multiple stages. Each stage consists of one or more plan fragments. Each plan fragment is instantiated into one or more fragment instances, and each instance is assigned to run on a specific BE node.

The relationship between two stages is a producer-consumer via data exchange: the upstream stage's fragment instance outputs data, and the downstream stage's fragment instance receives data. The shuffle mode determines how data is distributed from upstream to downstream.

The plan fragment received by the BE is the physical execution plan generated by the FE. It determines how fragment instances execute data processing on BE nodes.

## 4.2 Query Plan Generation and Stage Partitioning

### 4.2.1 Logical Plan Tree

The logical plan tree is a relational algebra operator tree derived from the SQL statement. Leaf nodes represent data sources (e.g., table scans). Internal nodes are relational algebra operations (e.g., filter, join, aggregate). The root node is the final operation, and its output is returned as the query result.

### 4.2.2 Physical Plan Tree

The physical plan tree is formed by transforming the logical plan tree. It selects a specific execution algorithm for each relational algebra operation. Each algorithm in the physical plan corresponds to an operator in the BE, where each operator is a concrete implementation of a relational algebra operation.

### 4.2.3 Stage

When generating the physical plan, the FE identifies operators that require cross-node data exchange (e.g., Hash Join, Hash Aggregation, Global Sort). It inserts Exchange nodes at these operators. The physical plan tree is partitioned into multiple subtrees at the boundaries of Exchange nodes, where each subtree corresponds to a Stage. Operators within the same Stage do not require cross-node data redistribution.

## 4.3 How Does BE Convert a Physical Plan Tree into a Stage Runtime Instance

The FE uses a Thrift data structure, TPlanFragment, to represent a stage. The FE uses a Thrift data structure, TPlan, to represent a physical plan tree within a stage. The FE uses a Thrift data structure, TDataSink, to represent the data output of a stage. The FE uses a Thrift data structure, TDataPartition, to represent the data partitioning strategy of a stage. The FE uses a Thrift data structure, TDescriptorTable, to represent the table and column descriptors for a stage. The FE uses a Thrift data structure, TPipelineFragmentParams, to encapsulate all the above structures and dispatch them to the BE.

TPipelineFragmentParams (Complete parameter package sent from FE to BE)

```text
    │
    ├── TPlanFragment              ← A Stage
    │       ├── TPlan              ← Physical plan tree (operator tree)
    │       ├── TDataSink          ← Data output (e.g., DataStreamSender)
    │       └── TDataPartition     ← Partitioning strategy
    │
    ├── TDescriptorTable           ← Table and column descriptors
    │
    ├── local_params               ← list<TPipelineInstanceParams>,
    │                                 one per fragment instance
    │                                 (fragment_instance_id, backend_num,
    │                                  per_node_scan_ranges, sender_id, ...)
    │
    └── query_globals / query_options / txn params (Other execution context)
```

After receiving TPipelineFragmentParams, the BE constructs a container, PipelineFragmentContext, as the runtime instance of the fragment. It instantiates Operators from each TPlanNode based on the node_type and other parameters, groups them into Pipelines, and registers tasks with the pipeline task scheduler.

## 4.4 Fragment Instance Runtime Structure

A PipelineFragmentContext consists of: 1. RuntimeState       (query id, fragment id, mem tracker, batch size) 2. Operator pipelines (the operator tree is split into Pipelines; nodes become Operators) 3. Sink operators     (DataSink is attached to the end of a Pipeline as a SinkOperator) 4. TaskScheduler      (Pipeline task scheduler drives tasks; no more PlanFragmentExecutor)

## 4.5 Fragment Execution Lifecycle and Data Flow

Data flow is task-driven. The Pipeline engine splits the operator tree into Pipelines at blocking operators, and the task scheduler executes PipelineTasks on a fixed-size thread pool.

Each PipelineTask repeatedly pulls a vectorized Block from its source operator, pushes it through the operator chain, and hands the result to the sink operator of that Pipeline. Cross-Pipeline collaboration is coordinated by Dependency / SharedState / DataQueue:

 - A task becomes runnable only when its source-side Dependencies are ready (e.g., the hash table of the build side is complete); otherwise it is blocked and descheduled, releasing the thread to other tasks.
 - Streaming hand-off between Pipelines (e.g., agg sink -> agg source) passes Blocks through a queue.
 - State that both sides need (hash table, sort buffer) lives in a SharedState owned by the pair of sink/source operators.

## 4.6 Shuffle

A Doris query is divided into multiple stages. Data is redistributed between stages via Shuffle.

The partitioning strategy determines how data is distributed to downstream instances: Broadcast: Upstream data is sent to every Fragment Instance of the downstream stage. Hash Partitioned: A hash value is computed for the data, and each row is sent to the matching Fragment Instance. Random: Data is sent to downstream instances in a round-robin manner for even distribution.

The downstream Fragment Instance uses ExchangeSourceOperator as the data input. Internally it holds a VDataStreamRecvr, which caches incoming Blocks in a SenderQueue; the operator pulls Blocks from the queue batch by batch.

### 4.6.4 Backpressure

```text

│                     │   ┌─────┐                │                            │

│                     │  (Done callback      │     pauses further sends       │
│                     │   suspended here)    │                                │
│                     └───────────┬──────────┘                                │
│                                 │                                           │
│         downstream consumes ◄───┘  memory drops below threshold             │

├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Upstream sender thread                  Downstream                        │
│   (same BE node)                          VDataStreamRecvr                  │
│                                                                             │
│        Block ──► ┌───────────────┐        ┌──────────────┐                  │
│                  │  mem(SenderQueue)+Block > threshold ?                   │
│                  └───────┬───────┘        │ SenderQueue  │                  │
│                          │ yes             │  ┌─────┐     │                  │
│                          ▼                 │  │Block│     │                  │
│                  ┌───────────────┐ ──wait──►│  │Block│     │                  │
│                  │ condition var │          │  └─────┘     │                  │
│                  │ (thread BLOCKED here)    └──────┬───────┘                  │
│                  └───────┬───────┘                 │ downstream consumes     │
│                          │ awakened                ▼ memory drops            │
│                          └─────────────  continue sending ◄─────────────────  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

After receiving data, the downstream VDataStreamRecvr evaluates whether the current memory usage of SenderQueue plus the incoming Block exceeds the threshold. If not exceeded: The Block is enqueued normally. The brpc Done callback is executed immediately, and the RPC response is sent back to the upstream  ExchangeSinkOperator right away. The upstream continues sending the next batch. If exceeded: The Block is still enqueued, but the brpc Done callback is suspended in a pending queue, and the RPC response is delayed. The upstream  ExchangeSinkOperator is blocked because it cannot receive the response, pausing further sends. When the downstream consumes data and memory usage drops, Doris actively triggers the Done callback. The RPC response is then sent, and the upstream is unblocked to resume sending. (Local Exchange Scenario): If the upstream and downstream instances reside on the same BE node, the sender thread is blocked on a condition variable when the memory limit is exceeded. The thread is awakened after the downstream consumes data, allowing the upstream to continue sending.

```text
│   └──────────────┘    │    └──────────────┘  owned by the sink-source pair, │
│                       ▼                        written by one side,         │
│             ┌──────────────────┐               read by the other            │
│             │ SharedState      │                                            │
│             │ (hash table /    │                                            │
│             │  sort buffer)    │                                            │
│             └──────────────────┘                                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

The Pipeline engine splits the operator tree into multiple Pipelines. It uses blocking operators and multi-input points as boundaries to divide the operator tree into multiple independently schedulable execution units.

Full-Data Processing Type (Sort, Aggregation, Analytic, PartitionSort): Must collect all input data before producing output. Index Construction Type (HashJoin Build, NestLoopJoin Build): Must build the hash table / dataset first before the Probe side can query. Multi-Way Parallel Input (Union): Creates an independent Pipeline for each subtree to achieve multi-way parallel input.

The split Pipelines interact through DataQueue / Dependency / SharedState, which respectively solve three types of cross-Pipeline collaboration: data transfer, execution ordering, and state sharing.

Dependency controls the execution order between Pipelines.

Pipeline A (Build)              Pipeline B (Probe)

```text
┌─────────────┐                 ┌─────────────┐
│  Build Sub  │                 │  Probe Sub  │
│      │      │                 │      │      │
│      ▼      │                 │      ▼      │
│  Build Sink │ ──Dependency──> │ Probe Source│
│ (Build Hash)│   (B depends A) │ (Probe Hash)│
└─────────────┘                 └─────────────┘
```

DataQueue enables streaming data transfer between Pipelines.

Pipeline A (Agg Sink)         Pipeline B (Agg Source)

```text
┌──────────────┐              ┌─────────────┐
│   Subtree    │              │             │
│      │       │              │  Agg Source │
│      ▼       │              │  (Output)   │
│   Agg Sink   │──DataQueue──>│             │
│(Pre-aggregate│   ┌─────┐    │  Read chunk │
│ Write chunk) │   │Block│    │   by chunk  │
└──────────────┘   │Block│    └─────────────┘
                   │Block│
                   └─────┘
```

SharedState enables state sharing between Pipelines.

Pipeline A (Build)            Pipeline B (Probe)

```text
┌─────────────┐               ┌─────────────┐
│  Build Sub  │               │  Probe Sub  │
│      │      │               │      │      │
│      ▼      │               │      ▼      │
│  Build Sink │               │ Probe Source│
│ (Write Hash)│               │ (Read Hash) │
└─────────────┘               └─────────────┘
        │                             │
        └── SharedState (Hash Table) ─┘
```
