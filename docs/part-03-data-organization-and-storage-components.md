# Part 3: Data Organization and Storage Components


## 3.1 Storage Hierarchy Overview

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                   Apache Doris BE Data Storage Architecture                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Tablet (Logical Storage Unit)                                             │
│      │ hash/range shard, 3 replicas                                         │
│      │ contains multiple Rowsets (MVCC versions)                            │
│      ▼                                                                      │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐                                  │
│   │Rowset v1 │  │Rowset v2 │  │Rowset v3 │  ← flush from MemTable           │
│   │[v1]      │  │[v2]      │  │[v3]      │  (immutable, each = one commit)  │
│   └────┬─────┘  └────┬─────┘  └────┬─────┘                                  │
│       each Rowset contains N Segments                                       │                                        │
│        ▼             ▼             ▼                                        │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐                                  │
│   │ Segment 1│  │ Segment 1│  │ Segment 1│                                  │
│   │ Segment 2│  │ Segment 2│  │ Segment 2│ ← Physical columnar files        │
│   │ ...      │  │ ...      │  │ ...      │  (256MB, encoded, compressed)    │
│   └──────────┘  └──────────┘  └──────────┘                                  │
│                                                                             │
│   MemTable ──flush──> Rowset ──contains──> Segment                          │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

Data organization hierarchy in BE:

 - Tablet: Logical sharding unit (hash/range partitioned), with multiple replicas. Each replica of a Tablet has its own independent MemTable.
 - Rowset: Immutable data unit generated by a single MemTable flush (corresponding to one commit on one Tablet). Each flush triggered by MemTable produces a immutable version of Rowset.
 - Segment: Each Rowset contains one or more Segment files. It is a physical file within a Rowset, default 256MB, columnar storage. The number of Segment files is controlled by data size and parallelism.

## 3.2 MemTable

MemTable is the in-memory write buffer in BE.

 - In-memory structure: an append-only vector of row pointers (DorisVector<RowInBlock*>). Rows are NOT sorted on insert.
 - Flush threshold: config write_buffer_size (default 200MB; 100MB for aggregate-key tables), adaptively shrunk under BE-wide memory pressure.
 - Write path: rows are appended to the vector; at flush time the rows are sorted by schema key (pdqsort), then AGG/UNIQUE keys are aggregated (and, under memory pressure, an in-memory shrink pass may sort + aggregate early).
 - Flush triggers: - MemTable memory reaches the (adaptive) write_buffer_size - Load task ends (DeltaWriter close) — ALWAYS flushes - BE-wide memtable memory pressure (memtable_memory_limiter)
Lifecycle:

```text
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │                        MemTable Lifecycle                                   │
 ├─────────────────────────────────────────────────────────────────────────────┤
 │                                                                             │
 │   ┌──────────┐                                                              │
 │   │ Create   │     Spawned by DeltaWriter when a load task targets a Tablet │
 │   └────┬─────┘                                                              │
 │        ▼                                                                    │
 │   ┌──────────┐     Rows arrive via BRPC/HTTP and are appended to an         │
 │   │  Write   │     in-memory row vector, unsorted; no aggregation yet.      │
 │   └────┬─────┘                                                              │
 │        ▼                                                                    │
 │   ┌──────────┐     Flush triggers (any of):                                 │
 │   │  Flush   │      • Size reaches write_buffer_size (default 200MB,        │
 │   │          │        adaptive; 100MB for aggregate-key tables)             │
 │   └────┬─────┘      • Load task ends (DeltaWriter close) — ALWAYS flushes   │
 │        │            • BE memory pressure forces early flush                 │
 │        ▼                                                                    │
 │   ┌──────────┐                                                              │
 │   │ Segment  │     Ordered output → Column Encode → Compress → Build Index  │
 │   └────┬─────┘     → Write to Segment file(s) (split at ~230MB = 90% of the │
 │        │           256MB hard cap)                                          │
 │        ▼                                                                    │
 │   ┌──────────┐                                                              │
 │   │  Rowset  │     Rowset metadata registered with version info.            │
 │   └────┬─────┘     Rowset is active. Rowset is visible to queries           │
 │        ▼                                                                    │
 │   ┌──────────┐                                                              │
 │   │ Destroy  │    Memory buffer released; MemTable object destroyed         │
 │   └──────────┘                                                              │
 │                                                                             │
 │   Key Rule: A MemTable is ALWAYS destroyed after flush, whether it was      │
 │   full or not. The DeltaWriter may create a new MemTable if the load        │
 │   task continues, or close entirely if the task is finished.                │
 │                                                                             │
 │   Note: Each replica of a Tablet maintains its own DeltaWriter, which in    │
 │   turn manages its own MemTable independently.                              │
 └─────────────────────────────────────────────────────────────────────────────┘
```

Important Note on DeltaWriter: Even if a MemTable contains only a small amount of data (e.g., 1MB), it will be flushed when the load task ends. This is why frequent small loads generate many small segment files, increasing compaction pressure and degrading scan performance. Mitigation: use client-side batching or enable server-side Group Commit.

## 3.3 Rowset

Rowset is the atomic data import unit in Doris BE.

 - Generated by a single MemTable flush (corresponding to one commit on one Tablet replica).
 - Contains one or more Segments (columnar files).
 - Versioned for MVCC and consistent reads.
 - The unit of Compaction and data visibility.
Lifecycle:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                              Rowset Lifecycle                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌──────────┐                                                              │
│   │ Create   │  Generated by MemTable flush (single commit on one replica)  │
│   │          │  Assigned a unique version.                                  │
│   └────┬─────┘                                                              │
│        ▼                                                                    │
│   ┌──────────┐     Rowset metadata registered with version info in          │
│   │  Active  │     TabletMeta;Visible to queries; participates in MVCC reads│
│   └────┬─────┘     TabletMeta maintains the Rowset version list             │
│        │                                                                    │
│        │  New Rowsets continuously created by load / stream load's flush    │
│        ▼                                                                    │
│   ┌──────────┐     Selected by Compaction policy (size-based / time-based)  │
│   │ Compact  │     Multiple Rowsets merged into one new Rowset              │
│   │          │     New Rowset gets a new version; old Rowsets marked stale  │
│   └────┬─────┘                                                              │
│        ▼                                                                    │
│   ┌──────────┐     No longer visible to new queries; retained for           │
│   │ Obsolete │     in-flight queries holding references                     │
│   └────┬─────┘                                                              │
│        │  Reference count drops to zero (no active scanners)                │
│        ▼                                                                    │
│   ┌──────────┐     Physical Segment files deleted; metadata removed from    │
│   │ Destroy  │     TabletMeta; disk space reclaimed                         │
│   └──────────┘                                                              │
│                                                                             │
│   Key Rules:                                                                │
│   • Rowset is IMMUTABLE after creation.                                     │
│   • Compaction produces a NEW Rowset; old Rowsets are NOT modified.         │
│   • Obsolete Rowsets are kept until all referencing queries finish (MVCC).  │
│   • TabletMeta garbage-collects obsolete Rowset versions periodically.      │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 3.4 Segment

Segment is the minimum physical storage unit in Doris BE.

 - Hard-coded upper bound of 256MB per segment file
 - Column-oriented file format containing encoded data and indexes.
 - Each Segment stores a portion of a Tablet's data for a specific row range.
 - Doris reads data at Page granularity within Segments.
 - Generated by flushing MemTable to disk during data ingestion.
Rowset and Segment relationship:

 - A Rowset contains one or more Segments.
 - Segments are split by size threshold (~230MB = 90% of the hard-coded 256MB cap).
 - Segments within the same Rowset share the same version and transaction context.
Lifecycle:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                        Segment Lifecycle                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │

│   └────┬─────┘     Visible to queries; loaded by scanners on read           │
│        │                                                                    │
│        │  Compaction triggered (size / time / cumulative policy)            │
│        ▼                                                                    │
│   ┌──────────┐     Multiple Rowsets (and their Segments) merged             │
│   │ Compact  │     New Segments generated; old Segments unchanged           │
│   │          │     New Rowset registered with a new version                 │
│   └────┬─────┘                                                              │
│        ▼                                                                    │
│   ┌──────────┐     Belonging Rowset marked stale in TabletMeta              │
│   │ Obsolete │     No longer visible to new queries                         │

│   └────┬─────┘                                                              │
```

## 3.5 Tablet

Tablet is the logical data partitioning (sharding) unit in Doris.

 - Created by hash/range partitioning of a table.
 - Each tablet has multiple replicas (default 3) across BE nodes.
 - Contains multiple Rowsets (versioned data imports).
 - The unit of data distribution and parallel query processing.
Tablet and Rowset relationship:

 - A Tablet accumulates multiple versioned Rowsets.
 - VersionGraph tracks visible Rowsets for MVCC.
 - Compaction merges Rowsets to optimize storage.
Each Tablet replica maintains its own TabletMeta (local metadata), tracking schema, version history, and Rowset list.

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                        Tablet Lifecycle                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌──────────┐                                                              │

│   │          │  Assigned to BE nodes; each BE initializes a replica         │
│   │          │  → TabletMeta created (schema, initial version graph)        │
│   │          │  → Empty Rowset [0-1] registered                             │
│   └────┬─────┘                                                              │
│        ▼                                                                    │
│   ┌──────────┐     Receives writes: MemTable flush → new Rowset versions    │
│   │  Active  │     TabletMeta tracks version graph for MVCC reads           │
```

## 3.6 Partitioning

### 3.6.1 What Is a Partition

Doris manages a table's data in two layers, and the partition is the first of them: every row is assigned to exactly one partition by evaluating its partition key — one or more columns (or an expression) declared at table creation.

The partition divides the table logically; the unit of physical storage is the bucket

### 3.6.2 Partition Types: Range, List, and Unpartitioned

The three partition types differ in exactly one thing: how the value space of the partition key is cut into partitions.

```text
 ┌──────────────────────────────────────────────────────────────────┐
 │              Three ways to cut the key space                     │
 ├──────────────────────────────────────────────────────────────────┤
 │                                                                  │
 │  Range:        contiguous intervals                              │
 │  ┌──────┬──────┬──────┬──────┬──────┐                            │
 │  │      │ P1   │ P2   │ P3   │      │   key: dt (date)           │
 │  └──────┴──────┴──────┴──────┴──────┘                            │
 │        <'2025-01-01' <'02-01' <'03-01'                          │
 │                                                                  │
 │  List:         discrete value sets                               │
 │  ┌─────────────────────────┬───────────────────────┐             │
 │  │ P1: (BJ, SH)            │ P2: (GZ, SZ, ...)     │  key: city │
 │  └─────────────────────────┴───────────────────────┘             │
 │                                                                  │
 │  Unpartitioned: one cell                                         │
 │  ┌──────────────────────────────────────────────┐                │
 │  │ P1 (the default partition)                   │                │
 │  └──────────────────────────────────────────────┘                │
 └──────────────────────────────────────────────────────────────────┘
```

RANGE. The key space is divided into contiguous intervals. Each partition is declared with an upper bound, and rows fall into the partition whose bound just exceeds their key value — the mapping rule is "find the first bound greater than my value". Range partitioning is the natural choice for time and other monotonic keys, and it supports multiple partition columns (the interval is then a tuple-wise lexicographic bound). This is the type behind almost every time-series layout in Doris, and the one that the dynamic and auto partition machinery of 3.6.4 builds upon.

LIST. The key space is divided into explicit, discrete value sets: each partition declares the exact values it holds (one partition column), and a row belongs to the partition that lists its value. There is no ordering between partitions — a list partition is a labeled drawer, not an interval. Use List for categorical keys (region, tenant, status) where "the set of values" is the natural management unit: retiring one tenant's data is dropping one partition.

UNPARTITIONED. A table created without a PARTITION BY clause has a single default partition: the key space is not divided at all. Everything said about partitions elsewhere in this chapter still applies — there is simply one of them — and the table still has buckets inside that one partition (the second logical layer does not disappear; see 3.7).

### 3.6.3 From Declaration to Write

**Step 1 — The declaration lives in the FE Catalog.**

When a table is created, the FE parses the PARTITION BY clause and builds a PartitionInfo object (`fe/.../catalog/PartitionInfo.java`). PartitionInfo describes how the table's key space is divided into partitions; it comes in two flavors — RangePartitionInfo and ListPartitionInfo — one per table, covering all of its partitions. Each PartitionInfo has an idToItem map: the partitionId is the key, and the value is a PartitionItem(A RangePartitionItem holds a full [lower, upper) range of partition keys; a ListPartitionItem holds a set of explicit values (`RangePartitionItem.java`)). Whenever a partition is created, the FE also builds a Partition object to hold the partition itself: its name and its tablets. Every partition is identified by a globally unique partitionId, and every OlapTable keeps an idToPartition map from partitionId to Partition object (`OlapTable.java`), alongside a nameToPartition map keyed by name (`OlapTable.java`). A partition exists twice: once as an entry in PartitionInfo (the rule), once as a Partition object (the entity)

```sql
   CREATE TABLE sales (dt DATE, amount DECIMAL(10,2))
   PARTITION BY RANGE (dt) (
     PARTITION p2023 VALUES LESS THAN ("2024-01-01"),
     PARTITION p2024 VALUES LESS THAN ("2025-01-01") );
```

**Step 2 — The FE ships expressions, not a lookup table.**

Every write — INSERT, Stream Load, or Broker Load — is planned through OlapTableSink (`fe/.../planner/OlapTableSink.java`). The partition rule lives in the Catalog in two forms: the idToItem map (Step 1) and a partition expression stored alongside it (partitionExprs, seeded at analysis time via RangePartitionDesc). The planner ships the expression form: getPartitionExprs() (:543) is serialized into the load plan as partitionFunctionExprs (:548, :629) — conceptually a nested conditional that the BE evaluates per row at execution time, mapping the row's key to a partitionId. The expression is not the plan's only payload, though: the same partition parameter carries, for every partition, its num_buckets and its tablet array — the routing half of the rule, built by createPartition() alongside the expressions (OlapTableSink.java :554-667). A Range table and a List table therefore look identical to the BE execution engine — both are just "one expression per row, plus a key-space → partitionId map."

**Step 3 — Each BE evaluates the expression, row by row, locally.**

On the BE, the sink's row distributor feeds each incoming Block to OlapTabletFinder (`be/src/vec/sink/tablet_sink_hash_partitioner.cpp`; `be/src/vec/sink/vrow_distribution.cpp`), which evaluates the FE-supplied expression against every row: a binary search over the sorted range bounds, or a hash lookup in the list's value set. The result is a partitionId. A row that matches no partition is rejected right here — this is the boundary case noted in 3.6.1, enforced at write time.

```text
│    → on to bucketing            (the 3.6.1 boundary case,        │

└──────────────────────────────────────────────────────────────────┘
```

**Step 4 — From partitionId to tablet.**

The partitionId selects one entry from that plan-side partition parameter: the partition carries its num_buckets and its own tablet array, already loaded on the BE (Step 2). For a hash-distributed table, the BE chains CRC32 over the row's bucket-column values — each column folded into a running uint32, NULLs hashed as a fixed constant (tablet_info .h:241-253) — and takes the modulo: bucket_index = hash_val % num_buckets (:254). The tabletId is then a pure table lookup: tablets[bucket_index]. Random-distributed tables skip the hash and rotate among buckets instead (:257-264). Finally the row is routed, possibly to the BE itself and possibly to another, to the BEs that host that tablet's replicas (7.3, 7.8), where the actual write happens. Every step is a pure function of the row's key columns — no catalog round-trip is needed for any individual row.

```text
┌──────────────────────────────────────────────────────────────────┐
│        Step 4: From partitionId to tabletId                      │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   one row, already resolved to partition P (Step 3)              │
│        │                                                         │
│        ▼   P travels with the plan, carrying:                    │
│   ┌────────────────────────────────────────────┐                 │
│   │   P:  num_buckets = 10                     │                 │
│   │       tablets = [20001, 20002, ..., 20010] │                 │
│   └────────────────────────────────────────────┘                 │
│        │                                                         │
│        ▼  ① hash the bucket columns (tablet_info.h:241-253)      │
│    hash_val = 0                                                  │
│    for each bucket column:                                       │
│        value → hash_val = zlib_crc32(value, type, hash_val)      │
│        NULL  → hash_val = fixed null-hash constant               │
│        │                                                         │
│        ▼  ② modulo (tablet_info.h:254)                           │

│        │                                                         │
│        ▼  ③ table lookup — tabletId is read, not computed        │

│        ▼  ④ route (7.3, 7.8)                                     │
│    row ──► the BEs hosting tablet 20008's replicas               │
│            (the actual write happens there)                      │
│                                                                  │
│   Random distribution skips ①–②: buckets chosen by rotation or   │
│   fast_rand instead (tablet_info.h:257-264).                     │
│                                                                  │
│   Every step is a pure function of the row's key columns —       │

```

#### The mirror with the read side.

This forward evaluation is the exact mirror of partition pruning (3.6.2): the same expression is evaluated in both directions. At write time the row is known and the partition is computed (row → partitionId); at plan time the predicate is known and the partition set is computed (predicate → partitions). A table's partition declaration therefore serves both paths through a single piece of metadata.

#### One exception — AUTO PARTITION.

When a table declares automatic partitioning and a row matches no existing partition, the sink does not reject it: it collects the failing keys and issues a single createPartition RPC back to the FE (`be/src/vec/sink/vrow_distribution.cpp`; the service is defined in `gensrc/thrift/FrontendService.thrift`). Once the new partitions exist and the BE's catalog cache is refreshed, the rows are re-evaluated and written. This is the only branch of the write path that contacts the FE per failing batch; ordinary partitioned tables never do — which is precisely why the no-match row of 3.6.1 is an error for them.
